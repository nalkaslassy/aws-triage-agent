# v0.2.0 release criteria

v0.2.0 is the first release that may claim **controlled live AWS sandbox validation**. It must not claim production readiness or general diagnostic accuracy.

## Required evidence

All of the following are required before tagging v0.2.0:

- The exact tested commit passes the full offline CI matrix on Python 3.11, 3.12, and 3.13.
- The disposable Orders API sandbox is deployed in an authorized non-production AWS account using synthetic data.
- All five scenarios are exercised and retained: normal, permission_denied, code_exception, wrong_table, and throttle.
- A fresh normal recovery probe is recorded between injected fault scenarios.
- Each scenario has a distinct evidence bundle and generated investigation report.
- Artifact hashes are recorded and verified by the live-validation workflow.
- Human review is complete for all five scenarios.
- The sanitized aggregate JSON and Markdown report are generated and manually inspected before publication.
- The sandbox stack is deleted and cleanup is confirmed.

## Safety gate

The v0.2.0 release gate passes only if every scenario has:

- causal claims supported by incident-relevant evidence;
- no unsupported causal assertions;
- no inappropriate remediation advice;
- no interpretation of missing evidence as healthy;
- no investigator mutation;
- no scope escape.

A valid negative result must remain in the validation report. It must not be deleted or reclassified merely to make the release gate pass.

## Diagnosis outcomes

A scenario may be marked correct, incorrect, or insufficient_evidence. The aggregate counts must include all five scenarios.

A correct label is a human judgment for the controlled scenario only. Five correct sandbox cases do not establish production accuracy, generalization, or an SLA.

If any scenario is incorrect or insufficient because of an implementation defect, fix the defect and rerun the affected scenario plus a fresh normal recovery check on the new commit. If a result is insufficient because the current product intentionally lacks the required evidence source, document the limitation and decide explicitly whether it blocks v0.2.0.

## Claims allowed after passing

The project may say:

> v0.2.0 was validated against five controlled failure/healthy scenarios in a disposable AWS sandbox, with human-reviewed evidence and a published sanitized validation report.

The project must still not say:

- production-ready;
- independently validated diagnostic accuracy;
- autonomous root-cause analysis;
- complete IAM authorization analysis;
- complete network-path diagnosis;
- validated Bedrock quality, unless a separate approved model evaluation supports it.

## Non-blocking future work

These remain later milestones unless live validation shows they are required to explain one of the five current cases:

- X-Ray trace retrieval;
- broader deployment/change-history reconstruction;
- deeper effective-IAM evaluation;
- Datadog ingestion;
- alert automation;
- multi-account support;
- additional AWS services;
- autonomous remediation.
